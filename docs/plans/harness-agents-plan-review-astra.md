What this change does: The plan introduces Pi first, shared reasoning-model selection and separate Prompt Engineer/Console chats, then connects Console actions to existing frontend generation. Its overall direction preserves the application, but the execution plan is not ready as written.

Reviewed 2026-11-05 against current source, root AGENTS.md and CinemaPromptEngineering/AGENTS.md. Source facts below are static observations, not live verification. Team identity facts come from the user's supplied requirements, not an independently queried catalog.

## Must fix

2. **P1 — Lost-response reconciliation lacks a usable correlation key and reload policy.** Plan §4 proposes run ID plus `/queue` and `/history/{prompt_id}` even when the response containing prompt_id was lost. Actual active submission is inline in StoryboardUI.tsx:2944-2949 and 3373-3378; payloads contain prompt and client_id, not the application run ID. Runs live in a React ref map at :522-548 and are cleared on cleanup at :1050-1064. Thus neither server correlation nor crash survival follows from reusing GenerationRun. Smallest correction: explicitly own these submission sites, persist a minimal pre-submission command/run record, and define a supported server-visible correlation mechanism before promising recovery. Verify server support before choosing extra_data or caller-assigned IDs. If correlation cannot be established, retain submission_unknown across reload, require manual resolution, and never resubmit automatically. Also correct §2's client ownership claim: comfyui-client.ts:292-346 has a retrying submit method, but no caller was found in the inspected Storyboard TypeScript sources; it is not the inline active path. If adopted during extraction, remove ambiguous POST retries. Bridge-level deduplication alone cannot fix that method.

3. **P1 — Workflow persistence assumptions are false and stale bulk saves can undo revisions.** Plan §2 calls storage atomic; §7/T6 adds revision history and an awaited action without resolving the old writer. api/workflow_storage.py:105-123 writes directly with write_text; :128-186 bulk-writes snapshots and deletes records missing from the incoming set. StoryboardUI.tsx:1507-1519 still schedules bulk sync, and services/workflow-storage.ts:57-78 returns body-level failure without throwing. A pending stale snapshot can overwrite a newly attached revision or delete a newly saved record; an HTTP 200 can contain partial failure. Smallest correction: assign T6/T5 coordination over all writers, use atomic replacement for single records, enforce expected revisions at the server, serialize/cancel stale bulk saves, and check success/errors before reporting completion. Keep history outside bulk deletion scope. Explicitly specify failure handling between workflow save and panel/project persistence. A forced reload should be acceptance evidence, not a required operation inside every save action.

4. **P1 — The privileged browser bridge needs a concrete admission and targeting contract.** Plan §8 mentions loopback/session/bridge IDs but never says who can acquire or present them, which browser origin is accepted, or how two open projects are selected. Existing CPE main.py:89-90 permits wildcard origins; root AGENTS.md Security Considerations explicitly says there is no application-wide authentication. The inference is specific: merely binding a new command service to localhost does not establish that a browser connection is the intended application session. Smallest correction: require exact allowed origins, an unpredictable short-lived bridge credential obtained through a defined trusted bootstrap, and explicit session-to-tab/project binding with stale/disconnected rejection. Do not claim existing CPE authentication supplies this. Clarify that loopback means browser and gateway on the same machine; remote-served clients need a separately designed path or an explicit unsupported result. This is a new bridge boundary, not a demand to retrofit authentication across the app.
